# scv-codex 0.25.0-codex.1

Pins SCV Core 0.25.1 and registers the workspace guard.

**Skip this version.** The guard it shipped never ran once. `0.25.0-codex.2` is
the same release with the guard working, and its note is the one to read for what
the guard does.

## What it shipped

- The blocking `PreToolUse` guard from Core 0.25.0, registered at the plugin-root
  default path (`plugins/scv/hooks/hooks.json`), so `.codex-plugin/plugin.json`
  still declares no `hooks` key. That path had only ever been asserted in prose.
  It was measured on codex-cli 0.146.1.
- A correction to `references/journal-hooks.md`, which said the Codex plugin
  surface could not register hooks by itself and that blocking was unavailable.
  Both were wrong.
- A provenance gate in `branch-flow.yml`. A pull request that changes code has to
  carry the plan it came from, or declare `[no-plan: <reason>]` in its title.
- `/scv/` in `.gitignore`. The marketplace ships the whole tracked tree, so an
  `scv/` directory here would put our plans, conversations and hook-fed journal
  into every user's plugin payload.
- `docs/RELEASING.md`, a promote-wait fix, and "do not emulate this skill"
  wording on `promote`, `work`, `codegen` and `help`.

## The guard was inert

The hook command named `${CODEX_PLUGIN_ROOT}`. This host does not set that
variable — the hook environment carries `PLUGIN_ROOT`, with `CLAUDE_PLUGIN_ROOT`
as an alias, and no `CODEX_` equivalent. The path collapsed to
`/vendor/scv-core/core/template/hooks/guard.sh`, no such file was there, and
`bash` exited without the guard ever running.

Nothing looked wrong, because nothing was supposed to. The host proceeds when a
hook is missing or fails. The guard fails open on purpose, for the reason written
into `guard.sh`: one bug in it would deny every write in every project, while an
adversary would delete the file rather than corrupt it. So a guard that fails open
on a missing script and a guard with nothing to refuse produce the same thing —
no output, and the action allowed. The plugin was installed, the hook fired, every
write went through, and that is also what a healthy session looks like.

CI agreed. Every contract test passed on this build. None of them expanded a hook
command; they checked the JSON shape, the matchers, and the guard's own rules,
and all of those were correct.

## How it was found

By installing the released tag into a scratch Codex home and asking a real model
to write a plan file by hand. It wrote it. Instrumenting the hook showed it firing
four times, so registration and matching were fine, and the unset variable was the
whole failure.

`0.25.0-codex.2` uses `${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}`, since both are set
and neither is documented as the stable name. It also adds
`plugins/scv/tests/test-guard-registration.sh`, which expands every hook command
under only the variables the host actually provides and requires the result to be
a file that exists.
