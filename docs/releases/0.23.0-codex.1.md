# SCV for Codex 0.23.0-codex.1

Core `0.23.0` 을 pin 한다. 어댑터 쪽에는 dispatch 계약 수정이 하나 있다.

## 어댑터 변경

### Core 릴리스 알림을 실제로 수신한다

`core-sync.yml` 이 `client_payload.core_tag` 를 읽고 있었는데, 그 키는 Core 계약에
존재한 적이 없다. Core 가 보내는 키는 `version` / `tag` / `asset_url` /
`checksum_url` 넷이다. 그래서 요청 태그가 **항상 비어 있었고**, 매 실행이 최신
릴리스를 다시 조회하는 폴백으로 동작했다.

계약에 없는 키를 Core 가 맞춰 보내게 하는 대신 래퍼가 계약에 맞췄다. 해석된
버전에 semver 검증도 붙였다 — 이 경로는 값을 받은 적이 없어 미검증인 채였고,
값이 `vendor-core.sh --tag` 로 직행한다.

폴링 주기를 주 1회에서 매일로 바꿨다. sibling wrapper 는 매일인데 여기만 주간이라,
알림을 놓쳤을 때 폴백이 최대 7일 걸렸다.

## Core 0.23.0 이 가져오는 것

### 결정 로그가 실제로 작동한다

`scv/DECISIONS.md` 는 v0.22.0 에 도입됐지만 기록이 도달하는 경로가 없어 엔트리가
쌓이지 않았다. 아카이브 엔트리에 `path delta:` 한 줄이 생겼다 — 계획이 제시한
경로와 실제로 간 경로가 어떻게 달랐는지, 그리고 왜인지. 계획대로 갔다면
`as planned` 한 단어로 끝난다.

### 구현 원칙 4종

`work` 와 `codegen` 이 구현할 때 기본으로 지키는 것 — 기존 코드를 먼저 찾아
재활용, 현재 요구를 충족하는 가장 단순한 구현, 관심사 하나당 컴포넌트 하나,
되돌리기 비싼 결정은 장기 관점. PLAN 의 `Guardrails` 가 항상 우선한다.

### 쉬운 말 먼저

계획 설명과 진행 보고가 길고 어려워지는 것을 막는 규칙이 프로토콜 13개에 들어갔다.
짧게 먼저 말하고, 더 필요하면 그때 자세히.

### 계획서 린트가 실제 계획서를 통과시킨다

`check-frontmatter` 가 표준 문서 스키마를 promote 계획서에도 적용해, 문서화된
템플릿으로 쓴 계획서가 전부 거부되고 있었다. 계획서는 계획서 스키마로 검사한다.
